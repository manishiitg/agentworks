Server-Hosted Workflows, Local Agents

A workflow lives either on your laptop or on a shared server — never both. Agents always run on the laptop, so they use your own LLM login and your own browser. Several users can drive the same server workflow, each from their own laptop.

What is built

  • Router (workspace/remote_router.go) in the laptop's workspace-api: forwards any request inside a server workflow (documents, list/glob/search, folders, versions, upload, export/import, query/mutate/db, execute), merges listings and globs, rewrites the docs root both ways, keeps browser and tool-API commands local with their paths remapped to _system/remote-scratch/, rejects operations spanning two placements, shows an unreachable server's workflows as remote_status: unreachable.
  • Placement file outside the docs root: WORKSPACE_REMOTE_WORKFLOWS_FILE, default <parent>/.<docs-dir-name>.remote-workflows.json, written 0600. It holds server tokens, so no workspace tool or sandboxed agent can read or repoint it. agent_go (pkg/remoteplacement) reads the same file.
  • Remote workflow tool mode: server-placed workflows always use mcp_only, including Builder, Run, automated turns and workflow agents. Placement overrides saved native-tool settings and is rechecked before agent finalization; confinement cannot upgrade a remote workflow to native tools. Local workflows, Crew projects, Code and Vault retain their existing tool modes. Attaching a remote workflow to a local Crew does not move the Crew.
  • Token check before the router: every /api request needs the workspace token (or a verified per-user token) before anything is forwarded; /api/remote/* included.
  • Server mode (WORKSPACE_SERVER_USER_TOKENS_FILE): per-user tokens (SHA-256), identity pinned from the token, then server authorization (workspace/server_authz.go): route allowlist; every path inside a Workflow/<name> the caller may access per its workflow.json access lists, or the caller's _users/<id>/; owners/editors write and execute, readers read; no-access reads answer 404 (no probing of names); listings filtered; /api/execute runs under a server-computed Folder Guard (the workflow folder), only with a working sandbox; /health hides docs_dir; GET /api/remote/whoami for laptops.
  • Forwarding hygiene: SECRET_*, MCP_* and WORKSPACE_API_TOKEN are stripped from forwarded commands (and again on the server); the laptop's X-User-ID is never forwarded; https required except loopback; redirects are not followed; 75-minute timeout (above the 1-hour execute cap).
  • Moves: use server-mode-only /api/remote/workflow/import and /api/remote/workflow/export transport; the removed /api/workspace/* backup routes remain unavailable. Moves are serialized; refuse a non-empty server folder; stream the archive from a temp file; exclude .sandbox-cache; verify file counts; a failed move to the server removes the partial copy so it can be retried.
  • agent_go guards: CLI isolation without a local folder, Folder Guard paths created on the server, step working dir in local scratch, per-workflow SQLite stores and the local cost ledger skipped for server workflows, guard test TestNoNewDirectDocsRootAccess (WorkspaceDocsRoot() and getWorkspaceDocsAbsPath()).
  • Fixes for everyone: atomic document writes (kept alongside main's chat-log save), workspace import on macOS.

Found while testing (not predicted)

  • Code-execution tool calls are curl "$MCP_CUSTOM/…" shell commands; they must run on the laptop.
  • Folder Guard materialization created every granted directory on local disk before each step.
  • A move's empty-folder check on the server hit the new authorization as "no access"; fixed by answering no-access reads with 404, and covered by a round-trip test against the real server-mode engine.

01Summary

Example: a user has 10 workflows. 8 are local, 2 live on a team server. A teammate also works on those 2 server workflows from their own laptop.

WhyLocal agents

Agents use your own Claude / Codex / Cursor / Pi login and your own Chrome with its sign-ins. Neither can live on a shared server.

WhyServer workflows

One shared copy of a workflow that several people can open, run and improve — with no sync and no second copy.

Already thereTool plane

Remote workflows enforce mcp_only: workflow file and shell calls go bridge → local agent_go → workspace-api. Local workflows and products keep their existing native-tool policy.

MissingThe rest

Per-workflow routing, ~43 direct-disk reads in agent_go, server-side auth and sessions, browser split, secrets, locks.

Verdict: possible. Nothing found blocks it. The server only needs workspace-api plus auth, sessions, locks and folder versions — no coding CLIs, no LLM logins, no agent_go. This is from reading the code; the end-to-end spike in phase 0 is the first real proof.

  1. mcpbridge only forwards (mcpagent/cmd/mcpbridge/main.go:363-392). Headers: Authorization: Bearer MCP_API_TOKEN, X-Session-ID, X-Virtual-Scope-ID. It knows nothing about workflows.
  2. agent_go resolves the session to a workflow, user and folder guard. The folder guard is "set internally — never from LLM args" (agent_go/pkg/workspace/execute_shell_command.go:66-72).

Consequence: the only component that must learn "this workflow is on the server" is agent_go, at the point where it picks a workspace client for a session. The bridge and the CLIs don't change.

04Placement & routing

The July draft assumed the whole workspace moves, with one global WORKSPACE_API_URL. Mixed placement means the target is chosen per workflow.

LAPTOP                                                               SERVER
Claude → mcpbridge → agent_go ─┬─ local workflow:  files/shell/db → local workspace-api
                               ├─ server workflow: files/shell/db ─────────────────────→ server workspace-api
                               └─ any workflow:    browser        → local workspace-api → agent-browser → your Chrome

Design

  • Workflow location registry. The laptop keeps a list of connected servers (URL, server id, device token in the OS keychain). Server workflows appear under a path prefix such as _remote/<server-id>/Workflow/<name> in the laptop's path space.
  • One router. A single WorkspaceStore / client factory picks local or server by that prefix. Every workspace call goes through it — tools, plan tools, Crew, history, scheduler.
  • Per-session client. When a session starts, agent_go resolves its workflow once and binds the matching client. Tool handlers use the session's client, never a global URL.
  • Prompt paths per workflow. Prompts embed absolute paths (AbsWorkspacePath). A server workflow's prompts must use the server root (/app/workspace-docs), a local one the local root.
  • No cross-placement references in v1. A local workflow or Crew may not reference a server workflow's KB, context or sub-workflow, and vice versa. Block with a clear error.
  • Local workflows unchanged. The 8 local workflows keep working exactly as today. Only server workflows take the new path, which keeps rollout safe.

05Browser

The browser tool does not drive Chrome from agent_go. It runs the agent-browser CLI as a shell command through workspace-api (agent_go/pkg/browser/client.go:75-87), which connects over CDP to localhost:9222. So whichever workspace-api runs the command is where the browser runs. Sent to the server, it would look for Chrome on the server — and the server cannot reach a laptop behind NAT.

Design

  • Browser always runs on the laptop — built as a router rule: any /api/execute whose command runs agent-browser (or calls the tool API through $MCP_*) executes on the laptop's own workspace-api, even for a server workflow, with that workflow's paths remapped to _system/remote-scratch/. This also covers agents that call agent-browser through the shell tool, so no blocking is needed.
  • Copy files across machines. ArtifactTransfer / UploadTransfer (pkg/browser/types.go:25-37) assume browser and files share one workspace-api. For server workflows add: server file → laptop staging before a page upload; laptop → server (/upload) after a screenshot or download.
  • Live view and recordings stay laptop-side; recordings saved into the workflow are uploaded like any other artifact.
Why the split lives in agent_go, not mcpbridge: the bridge could run agent-browser itself, but it would bypass the CDP port config, folder guards, session tracking, live view and artifact transfer that agent_go already owns. Same result, much more rebuilding.

06Auth & identity

Today: workspace-api has one shared WORKSPACE_API_TOKEN, applied to process-execution routes (workspace/workspace_auth.go). User identity is whatever X-User-ID the client sends (workspace/handlers/documents.go:27, shell.go:50), and the folder guard arrives in the request body. Fine on one machine; unsafe on a shared server, where a modified laptop app could claim another user or send a wider folder guard.

Design

  • Connect a laptop: sign in on the server (existing users.json accounts), approve "Connect desktop", laptop exchanges a one-time grant for a device token scoped to that user + device. Revocable, listed per user, stored in the OS keychain.
  • Server derives identity from the device token on every request. X-User-ID is ignored for authority.
  • Server computes the folder guard from the session's workflow and the user's role on it (owner / reader via the existing Share model). Client-sent folder guards are ignored for server workflows.
  • Per-workflow sandbox on the server. A prompt-injected agent on user A's laptop can run shell on the server. Landlock must confine it to that one workflow's folders, so it cannot reach user B's data.
  • TLS only, request size and rate limits, audit log of who ran what.

07Sessions

Session IDs are the glue between the bridge, agent_go, and the server. Today the server never learns who owns a session.

TodayWhereProblem on a shared server
Each laptop's agent_go mints IDs: uuid.NewString(), or schedule-<trigger>--<id>_<nanos> for schedulesexternal_run.go:87, external_builder.go:74, scheduler.go:170Collisions are practically impossible, but nothing ties an ID to a user or device.
Session → workflow, user, folder guard lives only in agent_go memorycommon.SetSessionFolderGuardServer can't verify; lost when the laptop app restarts.
Server process ownership comes from RUNLOOP_SESSION_ID in the client-sent extra_envworkspace/handlers/process_manager.go:195-202Spoofable. /processes and /processes/cleanup aren't scoped per user, so one laptop can list or kill another user's background processes.
Live run events stream from the agent_go running the sessionSSE in agent_goUser B can't watch user A's live run; only the durable history.

Design

  • Register sessions on the server. Before a server-workflow session runs, the laptop calls e.g. POST /api/sessions {workflow, kind, laptop_session_id} with its device token. The server checks access, stores session → user, device, workflow, folder guard, started_at, and returns a server session id.
  • Every later call carries that id. The server checks the token's user owns the session and applies the stored folder guard.
  • Scope processes, browser artifacts and streams by session owner. List/cleanup only sees your own sessions; admins see all.
  • Heartbeat. The laptop renews the session while it's alive. On expiry the server kills that session's processes and releases its locks. Replaces time-threshold sweeps for server workflows.
  • Session is the lock holder — the workflow edit/run lock (§08) is held by a session, so a crashed laptop frees it automatically.
  • Put the device id in session metadata so audit, costs and history show which laptop ran what.
  • History: sessions of a shared workflow are stored on the server. Others see them read-only (existing read-only rehydration). Continuing someone else's session means starting a new session from that history — the live CLI is in their tmux.
  • Unchanged: MCP_API_TOKEN (bridge → local agent_go), tmux namespaces and tool-session ownership are all laptop-local.

09Secrets & integrations

  • Secrets break as-is. The encryption key is derived from each agent_go's own auth secret (deriveSecretsKey() → GetAuthSecret(), cmd/server/secrets_routes.go:107). A laptop cannot decrypt a server workflow's secrets. Design: the server decrypts and injects them into server shell commands; values never leave the server. Matches the existing "readers use, don't reveal" rule for shared secrets.
  • LLM / CLI logins stay on the laptop and are never copied to the server.
  • MCP servers and connections are per laptop. Gmail / Slack / WhatsApp connections (config/gmail-connections, config/whatsapp-sessions) and configured MCP servers live on each laptop, so a shared step may work for Alice and not for Bob. Design: a server workflow declares what it needs; the runner checks before starting and fails clearly if something is missing. Server-side notification connections can come later.

11CLI launch folder

Today the CLI starts inside the workflow folder (codingAgentWorkspaceWorkingDir, coding_agent_modes.go:110-116). For a server workflow that folder doesn't exist locally.

  • Launch the CLI in a per-session local scratch folder; write only CLI config there (.mcp.json, .cursor/, hooks, policy files).
  • Inject what the CLI used to pick up from disk: CLAUDE.md, @file references, .pi/APPEND_SYSTEM.md.
  • Bridge guidance: prompt paths are server paths; reach them through tools, never local disk.
Highest-risk item. A missed file loses context silently — no error. Needs a live end-to-end check per CLI (Claude, Codex, Cursor, Pi), not unit tests.

12Server write safety

  • Half-written files are a real bug today. workspace/handlers/documents.go:145 and :1070 use plain os.WriteFile. A dropped connection or crash can leave half-written JSON. Fix: write to a temp file and rename. Helps local setups too.
  • Lost updates. Writes carry the version they were based on (If-Match); the server rejects a write based on a stale version so one user can't silently overwrite the other's newer edit.
  • Path traversal, symlinks and absolute host paths must be rejected on every route: read, write, move, delete, shell, db, upload/import/export, restore/versions.

13Moving a workflow

  • Local → server: back up, upload, rewrite embedded absolute paths to the server root, verify, then delete the local copy. The "exactly one place" rule is enforced, not advised.
  • Server → local: the reverse, and the server copy is removed or archived.
  • Backups of server workflows run on the server. The laptop's Backup page must not try to back them up from local disk.

16Validation checklist

Auth, identity & sessions

  • Connect a laptop, then revoke its token: it stops working without an app restart.
  • Change X-User-ID, a folder guard, or RUNLOOP_SESSION_ID in a request: the server ignores or rejects it.
  • User A lists or cleans up processes: user B's processes are invisible and untouched.
  • Kill a laptop mid-run: its session expires, its processes stop, its lock is released.

Routing

  • With 8 local + 2 server workflows, every request for a server workflow hits the server, and every local one stays local.
  • execute_shell_command pwd on a server workflow runs on the server.
  • A local workflow referencing a server workflow's KB is blocked with a clear error.

Browser

  • Browser step on a server workflow uses local Chrome with its logins; the screenshot appears in the server workflow.
  • A page upload of a server file works.
  • agent-browser via shell on a server workflow is rejected.

Sharing

  • Two laptops open one workflow: one holds the lock, the other sees who and can't write.
  • Due schedule with both laptops online: runs once, on the pinned laptop.
  • Pinned laptop off: schedule shows waiting, doesn't run elsewhere.
  • A's edit shows up in B's workflow list.
  • Older app opens a workflow upgraded by a newer app: read-only with an update prompt.

Data & writes

  • Network cut mid plan edit: file is fully written or clearly failed, never half-written.
  • Two writes from the same base version: the second is rejected.
  • Path traversal, symlink escape and absolute host paths are rejected on every route.

Secrets

  • A server-workflow secret works from both laptops; neither can read its value; logs redact tokens and secrets.

17Open questions

Only the first two block work (phases 1 and 7). The rest have proposed defaults in §02.

  • Blocks phase 1: OK to expose a device-token-only workspace-api route on the live Confida server?
  • Blocks phase 7: may Confida's own web app also run the shared workflows, or only laptops?
  • Is the server auth a hardened mode of workspace-api, or a small auth/proxy in front of a private workspace-api?
  • Server session id: server-minted, or the laptop's id bound on registration?
  • Which _system stores (global costs, Pulse platform DBs) should also exist per server for shared visibility?
  • Device token lifetime and refresh for long runs.
  • Do server-side notification connections (Gmail/Slack) belong in v1?
