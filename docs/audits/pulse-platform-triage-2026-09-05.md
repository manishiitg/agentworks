## Follow-up investigation: three priority claims

All three have supporting current-code evidence. No production implementation was changed during this investigation.

1. **False scripted success — confirmed in retained runtime artifacts and current code.** Server A iterations 16 and 17, dev/logs/step-daily-ops-completion-check/execution/scripted_fast_path.json, record exit_code=1 and success=true. The associated completion_check.json has all_passed=false; execution-final-summary.json and run_metadata.json say completed. controller_scripted.go explicitly returns Success:true in its nonzero-exit branch when pre-validation passes. Output-shape validation is overriding process failure. Fix should preserve nonzero failure and validation diagnostics; retain the existing exit-2 terminal-refusal contract and distinguish any later successful repair attempt from this failed attempt.

2. **Multiline Python SQL extraction — confirmed using real scripts and SQLite EXPLAIN.** Seventeen static queries across six Sales Outreach scripts fail when only the first string literal is checked, but the complete AST-parsed SQL passes EXPLAIN against the current database opened mode=ro/query_only. Scripts: step-send-email-outreach, step-provider-lookup, step-import-company-list, step-select-backlog-candidates, step-check-email-replies, step-apollo-company-search. Current plan_drift_checks.go patterns terminate after the first quote. Example: INSERT INTO outreach_activity followed by another literal containing columns/values is wrongly tested as just INSERT INTO outreach_activity. No SQL writes or workflow scripts were executed. Fix should extract complete static strings and mark dynamic expressions unsupported instead of reporting fragment errors as schema defects.

3. **Scheduler archive misattribution — reproduced with the exact current reconciliation function in an isolated Go harness.** Before-set contains iteration-0/default; after-set contains an old failed run renamed iteration-315/default plus the new completed iteration-0/default. reconcileWorkshopRunOutcome returns failed=true for iteration-315/default because a new folder name bypasses timestamp checks. rotatePairedIterationZero performs precisely this rename. Real social-media schedule receipt 1187b3b3 started 2026-09-04 03:00:26Z and points to iteration-316, which completed; its error blames iteration-315, whose execution started Sept 3 at 16:11:56Z and failed that day. Server A receipt 09ec502f similarly points to completed iteration-15 but blames failed iteration-13, started hours before the schedule. This establishes a deterministic mechanism consistent with the incidents; the exact historical before-list was not retained. Fix should correlate immutable execution identity to the schedule invocation, preserving true failures and avoiding both renamed history and unrelated concurrent runs. Requiring current timestamps alone is insufficient for concurrency.

Recommended repair order after investigation: false scripted success, scheduler identity, SQL extraction. The first two corrupt reported outcomes; the third creates false drift alarms.

## Local fixes after investigation

- Saved-script execution: a nonzero process exit or execution error now remains a failed attempt even if artifact pre-validation passes. Diagnostics and the existing repair fallback remain available; exit-2 terminal refusals are unchanged.
- Scripted SQL drift checks: adjacent Python string literals are combined before EXPLAIN, including mixed single/triple quotes and intervening comments. Dynamic expressions are skipped instead of validating a misleading prefix. Regression coverage exercises multiline SELECT/INSERT against a test SQLite database.
- Schedule attribution (PLAT-242 mechanism): both execution-evidence detection and failed-run reconciliation now prioritize StartedAt, then CreatedAt, over folder-name changes. Rotating an old failed run cannot override a current successful run or count as a new execution. Timestamp-less legacy metadata still uses the existing name-only fallback; this is not a general solution for concurrent-run identity.

These are source fixes, not repairs to historical schedule records. No live workflow was run and no server was restarted. During the initial fix pass no database issue was closed; the subsequent user-authorized internal closures are recorded below.
