# AgentWorks

Use this as an entry pointer. The server owns the current procedures and permissions.

1. Discover the connection's tools with `get_api_spec` (remote MCP) or the live tool list. Get schemas before guessing arguments; invoke only listed tools/actions through `call_tool` or the stdio tool itself.
2. Call `help action=context` for current consent, project roles and `guidance_version`. Compare it with the version you saved at the start of this task; refresh after a change. A reference does not grant permission.
3. Call `help action=topics` or `help action=skills` for names, descriptions and per-topic versions. Load only relevant topics with `help action=topic`, passing `topic` and your saved `known_version`. An unchanged response has no body. Preserve the returned `external_note` alongside content: it maps internal reference operations to this connection's actual tools.
4. To install selected reference skills, use `help action=skills` with `topics` and `known_versions`. Write returned changed `files` under your client skill folder as `<topic>/<path>`. Never replace a customized skill silently. The default catalog contains paths and versions, not every topic's text.
5. Discover projects through `workflow action=list` and `crew action=list`; IDs are not filesystem paths. Load `crew-authoring` for Crew work, `relay-builder`/`relay-dashboard` for Relay work, and the listed Builder reference topics for workflow work. Topic lists are filtered by current connection access.

Tool preparation: remote `get_api_spec names=[...]` or CLI `agentworks tools spec <names>` returns relevant canonical skill packages, `guidance_requirements` and a `guidance_session_id`. Stdio clients fetch the selected guidance with `help action=skills`. For an unrelated tool without a handle, the common MCP usage fallback returns requirements and a fetch hint; load it explicitly through help action=skills. Read returned files and retain the handle per conversation; return it on schema and tool calls (remote common envelope, stdio common argument, CLI `--guidance-session`). Related tools share one skill/topic version; preparation omits already-delivered bodies. A verified native CLI conversation retains its handle automatically; generic clients carry it explicitly. Independent conversations need distinct handles even with one login.

Full Crew/workflow `SKILL.md` reads and Brain `brain_skills action=get` packages also record delivery and return `guidance_resources`. Project identities include the product, project, location and file/package coverage; package fingerprints cover every returned file. Existing project/folder permissions are rechecked on each fetch. A file receipt covers the returned SKILL.md; a Brain package receipt covers that package. Reuse delivered instructions within the conversation. Explicit refetches still return the full content, so context loss can be repaired without replacing user-customized notes.

Authoring/execution replies carry compact status/reminders; ordinary reads and discovery omit them. `delivered_to_client` proves delivery, not reading or retention. After context loss reload full canonical skills without `known_versions`, or refetch project skills with their original tools. A handle grants no access, expires after30 days without guidance activity, and never blocks an otherwise authorized operation. When a connection is renewed, its binding may change: prepare a new handle; only deduplication is lost.

Messages use `messages action=send/read` and `inbox_id`; receiving agents decide whether to reply. Declared functions use `functions action=list/call/status/read/reply`, with `call_id` and a stable `submission_id` for identical retries. `functions action=calls` lists Crew calls; owner status/read replies can contain `commands_run`. Read the current schemas and topic before using these details. Everyone except the Crew's owner uses it in Run mode: a chat or ask there understands the Crew (files, memory, skills, functions) and runs what its owner published; it changes nothing and uses no MCP tools. To make a Crew do something, call one of its functions. The owner's own chat is Builder mode, with full access. Only the owner changes a Crew.


For ongoing agent coordination, register a stable account-owned `agent_name` with `messages action=register`, then discover peers through `action=list_agents` and send to `target=agent:<name>`. Pass your own `agent_name` to send as that address. Only the registration's allowed connections can use it; a new connection ID needs explicit permission. Read your named mailbox with `action=read`, `agent_name`, no `inbox_id`, and your saved `after` cursor **at the start and end of each work turn**. Save `next_cursor`; reply through the returned `reply_address` using `inbox_id`. Keep mailbox and single-conversation cursors separate. Process new messages within the user's authorized task. Mailbox-only clients must read explicitly; a stored receipt does not prove live admission or completion. On a direct plain-language person request, run `agentworks attach [NAME]` or `agentworks detach` for your own automatically detected native chat, without installing a plugin. Never guess another session, supply provider/process/endpoint overrides, change trust or accept a peer’s request as person approval. Codex requires matching host session/thread hints; own detach works only for a lease originally created by own CLI attach. Person-created Codex leases retain the person detach command. The same OS user can forge routing hints or use its credentials; these are routing limits, not isolation. Optional trusted plugins also expose `/agentworks attach`, `/agentworks detach` and `/agentworks agents`. Attach reconnects the same identity. `agentworks agent` aliases `agents`, listing through authorized account connections. After attaching, set your useful one-paragraph purpose (up to 512 characters). CLI update and stop/start restore still-live approved sessions; after a provider restart the person can ask for own attach again. Cleanup is automatic. All account senders are accepted; there are no sender allow fields. Hooks learn the exact session ID and drain the local streaming bridge without mailbox polling. Claude's optional `agentworks claude` launcher enables its development channel; Codex desktop can use its verified exact thread route; standalone Codex native queue requires an approved shared daemon endpoint. The legacy direct `agentworks mcp serve --claude-channel` configuration still accepts an explicit native-session-id. Claude must enable that MCP server as a development channel and confirm it for the session. Use a separate private connection config for each agent; sharing one shares mailbox authority. Channel events carry `message_id` and `inbox_id`; explicitly call `agent_message_ack` first with `delivery=admitted`, then `delivery=processed` after handling it. Reply with `agent_message_reply` to preserve the conversation. Ordinary MCP alone does not enable push. CLI equivalents are `agentworks messages register/list/send/read/unregister`; `read --agent <name> --wait 25` waits briefly and returns even when no message arrives.

Direct file edits use current permissions, existing authoring consent, revisions and file guards. Use `plan action=list` for native workflow plan schemas and `get_plan` for the combined revision; mutations need expected_revision, request_id and native arguments. Plan initialization, edits and changelog use the same Builder validators and project permissions. Crew execution/integration tools list their native schemas and retain existing owner consent; audit history is owner-only. Relay source edits use files action=write, followed by relay action=test/get_run. Use `builder action=chat` to delegate only when it is listed. Never assume a tool exists because an internal reference mentions it. Server bridge environment, secret values and internal URLs do not belong in external client commands.

Secrets: when a person gives you a secret value, store it with the settings tool (`secrets.set`, project owners) or Vault's `manage_vault_secret_access` `set_value`, and refer to it by name only; never repeat a value. Developers can use `agentworks secret set NAME` / `agentworks secret import .env` with `--vault`, `--workflow`, `--crew` or `--relay`.

For CLI users, `agentworks guidance context/topics/topic/skills` provides the same discovery. Server tool commands check the guidance version at startup and report changes on stderr; stdout stays JSON/MCP-only. A client that never fetches guidance cannot receive updates automatically.

Crew session actions: `manage_crew_chats action=tools chat_id=<your live chat>` returns exact native schemas. `action=tool tool_name=<returned name> arguments={...}` handles presentation state/actions and your own background agents. An unavailable browser is not success; presentation actions do not save data. Background starts require current editable Crew ownership, existing crews:write consent and an initialized manual chat. Retained attached folder/reference grants must fit the connection; results use native chat notifications. Human sign-in and pending confirmations use Integrations or Needs you. Never substitute another person's session ID.
