# Schedules

Use `automations` with `scope=schedule` and only the actions listed in this chat or connection. Start with `automations action=list scope=schedule`. In MCP pass project (ID or name); product chat already binds its own project. Preserve IDs, timezone, enabled state and settings the person did not ask to change.

Use create/update/delete, enable/disable, run_now/stop and runs where offered. Repeating requests ("every N minutes/hours") use cron_expression and timezone; every 5 minutes is "*/5 * * * *". in_minutes/run_at and dated calendar entries are one-time only. State the reply's timing_summary so the person hears what was actually saved. MCP create/update take schedule with the advertised timing and action fields. A project schedule either sends a message to an agent or runs the project's Python workflow directly. A message schedule may hold several messages (`messages`, a list): they are sent in order in the same chat, each only after the previous turn has finished, so "then follow up with X" is a second message in the same schedule, not a second schedule. If a turn starts background steps, the run waits for them and hands their results back as the next turn. A new message schedule made in a chat runs in that chat when no chat is named; the person can name another chat or give it its own persistent chat (`run_destination` isolated). Don't ask when unstated. Made outside a chat (the Schedules page or external MCP), a schedule (message or workflow) gets its own persistent chat unless an agent is named. Every schedule runs in a named agent (by its chat id) or its own chat; there is no implied main chat, and a schedule whose agent was removed runs in its own chat. Preserve existing saved destinations. Workflow schedules use action `run` and a workflow target with typed inputs and optional saved settings; supply required inputs before enabling. Existing standalone workflow timers require conversion into project schedules, not a label change. Old plan files cannot run. The server stamps the caller and decides the next eligible time.

Read [timing and execution](references/operations.md) before changing clock/dependency settings or diagnosing a missed occurrence.

Sharing a schedule with the Team (optional both ways): only a repeating schedule that sends one message can be shared, never a workflow, a dated or one-time schedule, or an account. To share, read it with `list`, then `team_sync save_file` a JSON file `schedules/<new id>.json` in the Team's shared folder holding `kind: "schedule"`, `name`, `description` (optional), `cron_expression`, `timezone`, `message` and `when` (the reply's timing_summary). To add one, `team_sync files` / `read_file` it, confirm the time and message with the person, then `create` it in their own project with `enabled` false and tell them it is switched off until they say so. Never turn a teammate's schedule on without being asked, and never change the shared file when you only add a copy. To bring a copy up to date with a changed shared schedule (or update the shared one), follow "Updating a shared command, schedule or theme" in `panel-access` → `references/team/SKILL.md`.
