# Timing and execution

Use the current schedules schema; do not edit schedules.json by shell or generic file tools. Website, Builder and MCP use the same saved definitions and server clock. List before editing and preserve omitted settings.

- Recurring callers use a five-field cron and an IANA timezone. For **every 5 minutes**, use cron_expression="*/5 * * * *"; every hour is "0 * * * *". in_minutes:5 means **once in five minutes**, never every five minutes. Confirm the saved timing_summary after create/update, and never describe a dated schedule as recurring. Calendar callers use explicit dates/time and may carry per-date input. For a one-time reminder, use the admitted in_minutes/run_at or calendar fields. Check an already-finished task now before creating an unnecessary reminder. Keep reminders the person requested unless they ask to remove them.
- A message schedule sends to its saved agent and conversation. New message schedules default to their own persistent chat, listed after the first run; the person can choose an existing chat instead. If unstated, ask which they want. Preserve existing destinations.
- A Crew workflow schedule uses action `run` and a workflow target, with optional saved settings and typed inputs. It runs the Crew's saved Python workflow directly and records its result in the configured chat. Supply every required input before enabling it. Different tasks use inputs and saved settings in that single workflow. Do not teach old plan steps or custom-message workflow execution. Existing standalone workflow timers still need their separate conversion into Crew schedules; changing a label does not migrate them. Preserve any after condition, outcome, delay and explicit deadline.
- There is one durable clock. Missed ticks are not replayed on restart. A new occurrence keeps the existing two-minute late-slot admission limit. An occurrence already waiting for a dependency keeps its original scheduled time and dependency deadline/local day, even if its configured delay exceeds two minutes. A global pause holds that waiting occurrence without consuming it; resume rechecks its current timer and prerequisites. The global pause and disabled flags still apply.
- A busy destination keeps the latest waiting occurrence per schedule. A newer occurrence replaces that schedule’s older waiting one. Distinct schedules sharing a destination take turns, oldest due first. This ordinary busy-chat queue does not enforce dependency deadlines or local-day expiry and may start after midnight. Dependency-waiting occurrences use the separate expiry/revalidation rule above. A global pause keeps already accepted conversation-queued deliveries, including one-time timers, and the existing clock retries them after resume. This does not create or replay occurrences missed while paused or offline.

Use run_now only for a requested real run. It ignores the schedule’s timing and dependency conditions; do not use it as proof those conditions were met. Read runs and the actual terminal outcome; saved next_run or an accepted receipt does not prove completion. A native agent can finish without opening a terminal. Use the saved run outcome for that exact request; another message’s reply does not complete it. No text yet does not mean the agent has stopped or lost its session; tool work can continue before a reply appears. Report the global pause, current blockers and the relevant timestamps separately from old skipped history. Never resume paused schedules merely to verify a change.

For “new conversation each time” runs, Stop ends native work when that run created the session. In any persistent or shared chat—including a schedule’s own chat, Main chat or a named agent chat—Stop stops waiting and leaves the chat’s work alone. It does not pause future occurrences or other schedules. Use disable when the person wants future runs paused. A stopped run is not a completed answer; inspect the recorded outcome rather than treating message acceptance as completion.

There is one pause for all scheduled work across the platform. Through the current `automations` tool, use `scope="schedule"` with `action="scheduler_status"`, `pause_all` or `resume_all`; these actions take no project and require an administrator connection with `users:manage` consent. Ordinary schedule actions still require a project and retain their existing access rules. Crew chat uses the same native service. If you lack access, ask an administrator to change the pause from Schedules. Read current status before describing a pause; history does not establish the present state.
